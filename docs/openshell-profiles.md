# OpenShell usage profiles — proposal

## Purpose

`packages/rust/openshell/default.nix` builds the OpenShell CLI, gateway and
prover, and `home-manager-modules/openshell` runs a local gateway — but AI
sessions (including this one) still talk to models directly on the host. The
goal is to run agent sessions **through** OpenShell sandboxes so every model
call and tool invocation is policy-governed, logged, and contained.

All three profiles below share one requirement: the sandbox must be able to
reach the LLM inference defined in `home-manager-modules/opencode` — the
`halogen-server` provider, `http://127.0.0.1:11435/v1`
(model `halogen-qwen3.8-flash-next`).

## OpenShell concepts used

| Concept | Role in these profiles |
|---|---|
| **Provider profile** (`profiles/halogen-server.yaml`) | Declares the inference endpoint, its credential, and the binaries allowed to reach it. Attached providers contribute `_provider_*` network rules to any sandbox. |
| **Sandbox policy** (`profiles/{locked,limited,open}.yaml`) | `version: 1` policies defining `filesystem_policy`, `process`, and `network_policies` per tier; exported as `OPENSHELL_SANDBOX_POLICY` by the home-manager module. |
| **`host.openshell.internal`** | Network policy never authorises loopback destinations, so `127.0.0.1:11435` cannot be written as-is. The gateway host is addressed via this SAN (generated by `openshell-gateway generate-certs --server-san host.openshell.internal`); the gateway dials the host listener on the sandbox's behalf. |
| **Binary matching** | Rules authorise *executables*, not shell commands. This is how the opencode `permission.bash` deny list is codified at the OpenShell layer (mapping table below). |
| **Enforcement modes** | `enforce` on credentialed/API endpoints; new scopes for a running sandbox go through `--approval-mode manual` rule proposals rather than silent policy growth. |

## The three tiers

| | locked | limited | open |
|---|---|---|---|
| **Intent** | Offline AI, minimal tools | Explicit scoped targets (e.g. GitHub) | Minimal restrictions, opencode policy only |
| **Providers attached** | `halogen-server` | `halogen-server`, `github` | `halogen-server`, `github` (read-write variant), `openai`, `anthropic`, `openrouter`, `deepinfra`, … |
| **Network** | Inference endpoint only | + GitHub family, Nix cache | + all AI provider APIs, Nix infra, web search, context7, Atlassian MCP, docs, ghcr.io |
| **Tools** | opencode, curl | + git, gh, nix | full image toolchain minus denied runners |
| **Filesystem** | workdir + `/tmp` writable, `/usr /lib /etc` read-only | same | same |
| **Process** | non-root (image USER fallback) | same | same |

## Codifying the opencode deny list in all profiles

`home-manager-modules/opencode` defines a `permission.bash` policy
(default `ask`, explicit allows, explicit denies). OpenShell enforces the
same intent through a different mechanism — paths, endpoints, and process
identity instead of command strings. The first column summarises related
rules rather than quoting each glob verbatim (e.g. the npm row covers
`npx*`, `bunx*`, `pnpx*`, `pnpm dlx*`, `yarn dlx*`, `npm install*`,
`npm i *`, `npm ci*`, `yarn install*`, `yarn add*`, `bun install*`,
`bun add*`, `pnpm install*`, `pnpm add*`, `volta install*`,
`corepack enable*`, `corepack prepare*`):

| opencode deny rule | OpenShell encoding |
|---|---|
| `rm -rf*`, `dd *`, `mkfs*`, `chmod 777*`, `chmod -R 777*`, `:(){*` (fork bomb) | `filesystem_policy.read_write` is the workdir + `/tmp` + `/dev/null` only; `/` is never writable, so destruction is contained to the workspace. |
| `shutdown*`, `reboot*`, `halt*`, `poweroff*`, `init *` | No privilege: non-root `process.run_as_user`, no systemd control access from the sandbox. |
| `kill -9*`, `killall*`, `pkill*` | Non-root uid limits signals to the sandbox's own process tree. |
| `sudo*`, `su *`, `doas*` | Non-root process identity; the binaries are absent from the image. |
| `curl*|*sh`, `wget*|*sh` | `curl` is only authorised to allow-listed endpoints, so remote code can only come from vetted hosts. |
| `npx*`, `bunx*`, `pnpx*`, `pnpm dlx*`, `yarn dlx*`, `npm install*`, `yarn add*`, `bun add*`, `volta install*`, `corepack *` | `registry.npmjs.org` is absent from every tier's allow-list. `npx` executes as `node`, and binary-scoped rules give `node` no route to the npm registry. |
| `uvx*`, `pipx *`, `pip install*`, `uv pip install*`, `poetry *`, `pdm *`, `conda *`, `mamba *` | `pypi.org` / `files.pythonhosted.org` absent from every tier's allow-list. |
| `cargo install*`, `cargo binstall*` | `static.crates.io` / `index.crates.io` absent. |
| `go install*`, `go run *://*` | `proxy.golang.org` absent. |
| `deno run http*`, `deno install*`, `deno add*` | `deno.land` / `registry.npmjs.org` absent. |
| `gem install*`, `bundle *`, `composer *` | `rubygems.org` / `repo.packagist.org` absent. |
| `nix-env -i*` | Same `nix` binary that `nix build` uses (OpenShell matches paths, not flags) — the flag-level distinction remains enforced by the opencode layer; the cache endpoint itself is allowed, matching `nix* = allow`. |
| `brew install*`, `port install*`, `apt(-get) install*`, `yum/dnf/zypper/pacman/apk install*`, `snap/flatpak install*` | Absent from the Linux sandbox image; their hosts (e.g. `snapcraft.io`, `flathub.org`) are not allow-listed. |
| `docker run*`, `docker pull*`, `podman run*`, `podman pull*` | No Docker/Podman socket is mounted into the sandbox; `registry-1.docker.io` is not allow-listed (only `ghcr.io` reads, for `dockerTools.pullImage`). |
| `git push --force*`, `git push -f*`, `git clean -fd*`, `git reset --hard*`, `git *--no-verify*`, `git commit* -n*` | opencode-layer (flag-level). OpenShell's GitHub provider grants clone/fetch only — `git-receive-pack` is absent, so push is impossible in `locked`/`limited`; the `open` tier's read-write GitHub variant allows push but cannot distinguish `--force` at the HTTP layer. |
| `find*delete*`, `find*-exec*rm*` | Contained by the workdir-only writable root. |

## Wiring

The module merges `providers` by id into one global catalog and merges
`policies` into the single `OPENSHELL_SANDBOX_POLICY`, so a tier is selected
at Nix level (catalog = union, policy = active tier):

```nix
services.openshell = {
  enable = true;
  gateways = [ /* as today */ ];

  # Catalog: shared inference profile + the tier's provider set.
  providers = [
    ./profiles/halogen-server.yaml
    "${openshell-shared}/share/providers/github.yaml"
    {
      id = "github";
      binaries = [ "/usr/bin/git" "/usr/bin/gh" ];
    }
  ];

  # Active tier: locked | limited | open
  policies = [ ./profiles/limited.yaml ];
};
```

Running a session per tier:

```bash
# locked: inference-only agent session
openshell sandbox create --name ai-locked --provider halogen-server -- opencode

# limited: + GitHub and Nix
openshell sandbox create --name ai-limited \
  --provider halogen-server --provider github -- opencode

# open: attach the wider provider set; policy comes from
# OPENSHELL_SANDBOX_POLICY (exported by the module)
openshell sandbox create --name ai-open \
  --provider halogen-server --provider github --provider openai -- opencode
```

Because the module exports `OPENSHELL_SANDBOX_POLICY`, `sandbox create`
picks up the active tier's policy without `--policy`.

## Caveats and follow-ups

1. **Version drift**: the repo pins OpenShell v0.1.3; the docs describe
   v0.1.6. Validate each file with
   `openshell profile lint -f home-manager-modules/openshell/profiles/halogen-server.yaml`
   against the pinned CLI before importing. The profile omits `tls` (the
   v0.1.3 schema accepts only omission or `skip`; `skip` would disable L7
   inspection and credential injection on a credentialed endpoint).
2. **Image layout**: `binaries` paths (`/usr/local/bin/opencode`,
   `/usr/bin/git`, …) assume an FHS-style sandbox image, matching the
   existing `github` provider entry. Adjust to the actual image, listing
   real paths rather than symlinks.
3. **Flag-level rules**: OpenShell matches executables, not arguments.
   Rules like `npx` vs `node` or `git push --force` vs `git push` remain
   opencode-layer concerns; OpenShell contains their blast radius instead.
4. **opencode provider config**: the `halogen-server` block in
   `home-manager-modules/opencode` carries a TODO to derive from common
   config. Once sessions run inside sandboxes, the OpenShell placeholder
   model supplies `OPENAI_API_KEY` to the client process from the attached
   provider, replacing per-config key handling.
5. **Gateway TLS**: the module registers the gateway with `disable_tls` on
   loopback; moving the gateway behind HTTPS/Tailscale (per the opencode
   TODO) is the natural follow-up before running untrusted agent code.
